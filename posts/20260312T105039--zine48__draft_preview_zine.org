** [[https://susam.net/writing-first-tooling-second.html][Writing First, Tooling Second]] by Susam Pal
:PROPERTIES:
:CUSTOM_ID: 62B8FFFC-819D-4215-85F9-D8E5EA3FF756
:END:

#+begin_quote
渴望建立个人网站的作者们总是长久地纠结于该使用哪种博客引擎、
选择哪种静态网站生成器、挑选哪种模板语言等等。
_我认为，在你的网站上发表至少五篇文章之前，这些都不重要。_
_先写纯 HTML，以后再操心工具的事。_
#+end_quote

确实，很多作者花很多时间捣鼓博客的样式、构建等，但博客文章却寥寥无几。
除非本身就是为了学习技术捣鼓博客构建，否则更重要的还是多写些内容，
当写得足够多，能够保持一定频率输出的时候，再慢慢考虑构建、优化样式。
很多时候，直接写 HTML 就够了。

#+attr_html: :role note
#+begin_section
如果你不熟悉 HTML，推荐看 [[https://htmlforpeople.com/][HTML is for people]]。
关于样式设计，作者有一份现成的样式表： [[https://github.com/susam/spcss?tab=readme-ov-file][SPCSS]]，也可以参考一下 [[denote:20250910T140613][我的博客设计]]。
#+end_section

如果不想写 HTML，也可以用 Markdown 或任何喜欢的纯文本格式编写，用类似 [[https://pandoc.org/][Pandoc]] 的工具转换成 HTML。

总之，如果创建博客的的初衷是写文章，那就先写上几篇，再考虑其他事情吧。

发现作者也用 Emacs，他的 [[https://github.com/susam/emfy?tab=readme-ov-file#line-by-line-explanation][Emacs for You (Emfy)]] 可以作为一份 Emacs 入门参考配置，解释也很详细。

** [[https://idiallo.com/blog/how-do-we-get-developers-to-read-the-docs][How Do We Get Developers to Read the Docs]] by Ibrahim Diallo
:PROPERTIES:
:CUSTOM_ID: 5A7EC738-9E07-46A7-80D5-8C5F22540505
:END:

写文档的时候很容易写成大而全，信息太多会导致主线脉络不清晰，过多信息和信息不足，效果是一样的。

这篇文章主要是关于 API 文档的，API 文档主要面向两类读者，一类是 API 的使用者，一类是 API 的维护者。
对于使用者来说，他只需要知道怎么用，他不太关心背后的细节；
对于维护者，他会关心更多为什么，希望尽可能多地了解 API 的设计细节，从而避免出错。
两者对于文档的需求是不同的，使用者期望的是清晰简洁的文档，快速知道 API 的作用、需要什么参数、用例；
维护者则期望更多技术细节，API 是怎么设计的、如何变迁的、为什么需要某个参数。
一个糟糕的文档是企图平等地服务于这两类读者，结果就是，对于使用者来说不够简洁，不能快速浏览；
对于维护者来说又不够深入和严谨。

作者认为，对于使用者，最好的文档首先是 API 本身，保持 API 的一致性，遵循清晰且可重复的模式，
让用户可以推断 API 的使用。
例如如果存在一个这样的 API ~/users/orders/1234/cancel~ ，
如果设计的好的话，用户可以推断，可能也存在一个 ~/users/orders/1234/update~ API。
其次，在写文档的时候要保持克制，不要阐述过多的细节，
用户不需要知道你为了兼容旧版本的 API 做了什么，你只要告诉他「兼容旧版本」就足够了。
作者的这句话我觉得讲得很精辟：
_「就像你不会为了解释每一行代码而写注释一样，文档也不会从过多的信息中获益。([[https://idiallo.com/blog/how-do-we-get-developers-to-read-the-docs#:~:text=The%20same%20way%20you%20don%27t%20write%20a%20comment%20to%20explain%20every%20line%20of%20code%2C%20a%20documentation%20doesn%27t%20benefit%20from%20too%20much%20information][Source]])」_

作者的建议是将额外信息@@html:<em>折叠</em>@@起来 (例如利用 ~<details>~)，
这样文档可以保持简洁，让使用者得以快速浏览获取信息；
对于维护者，他们可以展开折叠部分，了解更多细节。
而在文章组织上，也采取由浅入深的结构，先解释是什么，接着是怎么用，最后才是为什么，
而「为什么」这个部分还可以折叠起来。
作者又来了一个精辟的比喻：

#+begin_quote
把这想象成一个设计良好的错误信息。
一条好的错误信息会用通俗易懂的语言告诉你出了什么问题。
一条极佳的错误信息还会包含可展开的堆栈跟踪，但它不会先向你展示堆栈跟踪。

你的文档也承担着同样的工作。
先给人们他们正在寻找的答案，然后为那些愿意深挖的人提供深度内容。

[[https://idiallo.com/blog/how-do-we-get-developers-to-read-the-docs#:~:text=Think%20of,dig][Source]]
#+end_quote

另外考虑将给维护者看的内容拆分到别的文档里，通过拆分，可以保持使用者文档的简洁，
而在编写维护者文档时也可以写得很深入，不用去考虑初学者。

#+begin_quote
文档的目标不是完整性。
完整性是你写给自己的，为了让自己觉得完成了工作。
_文档的目标是在正确的时刻，将正确的信息传递到正确的人的脑海中。_

[[https://idiallo.com/blog/how-do-we-get-developers-to-read-the-docs#:~:text=The%20goal,moment][Source]]
#+end_quote

以我自己为例，我之前写过一篇关于 Emoji 正则匹配的文章，你可以对比一下前后两个版本：

- 2024 年 10 月 13 日归档版本：[[https://web.archive.org/web/20241013094934/https://taxodium.ink/emoji-regexp.html][Emoji 正则匹配]]
- 当前版本：[[https://taxodium.ink/emoji-regexp.html][Emoji 正则匹配]]

在归档版本，关于「Unicode character class escpae」、一些 String 的相关方法是直接呈现在正文的，
看起来内容很多，但会显得比较杂乱。

- [[https://lucida.to/][Lucida]]

  一个我目前用过的下载体验最好的音乐下载服务，
  大部分我想听的歌都能找到，而且可以按照专辑打包下载；
  专辑里通过编号也确保了歌曲的顺序，很贴心。
  下载时候的加载动画也很有趣，或是打鼓，或是旋转的 CD。
  我现在有空就会去下载一张专辑，放到我的播放器里听，慢慢收集那些 [[file:index.org::#album][喜欢的专辑]]，
  给播放器里那些 [[https://en.wikipedia.org/wiki/MP3][MP3]] 升级到 [[https://en.wikipedia.org/wiki/FLAC][FLAC]]，看看音质有没有提升。

  歌曲下载下来，哪怕断网了，或者流媒体服务挂了，也还能听到。
  如果下载的是无损的音乐，音质理论上也会更好一些。

  #+attr_html: :role note
  #+begin_section
  相比音质上的提升，更重要的是认真地、专注地、投入地听歌，
  哪怕是音质一般的音乐，也能听到很多平时没有留意到的细节。
  #+end_section

  Lucida 提供了好几个下载渠道，不过目前只有 Tidal 和 Amazon Music 是没问题的，其他渠道都会报错。

  在找歌曲的时候，可以通过专辑、歌手名、歌曲名尝试搜索；
  如果找不到，可以试试切换不同的渠道搜索；
  有时简体中文找不到，可以试试繁体中文，尤其是一些台湾的音乐人；
  像是日文，找不到的时候也可以试试英文、罗马音搜索；
  当你找到一个音乐人的时候，也可以点击他的名字，看看有没有关联相关的专辑或歌曲。
  不过一些平台上没有收录的就完全没办法了，例如一些比较早的专辑，一些从来不发流媒体的音乐人。
  如果总是失败，可以看看 [[https://status.lucida.to/status/lmbr][Status]] 页面，看看 API 状态是否正常，等正常了再尝试。
  有的歌搜索不到，可以先去对应的平台搜索看看没有，例如去 Tidal、Amazon Music 先搜索一下，
  如果在那上面可以找到，将专辑/歌曲页面的 URL 复制到 lucida 搜索，或许就能找到。

  Lucida 默认是以最高音质下载的，但我发现有时下载下来的是 [[https://en.wikipedia.org/wiki/Opus_(audio_format)][Opus]] 格式，文件体积很小，
  可能是因为 Lucida 是从流媒体上抓取的，原始的就是压缩过后的 Opus 格式，而不是无损格式。
  所以我一般都会选择转换成 FLAC，虽然从 Opus 转 FLAC 未必能还原音质。
  如果你很在意下载的是不是无损，你可以用 [[https://fakinthefunk.net/en/][Fakin' The Funk?]] 去验证一下。
  不过就算发现不是无损，又能如何呢，再花很大的精力找到无损的版本？
  很喜欢的专辑或许值得这么做，偶尔听听的专辑，我是不想花这个力气。
  再说，我也未必真能听出区别。

  下载下来的数据，除了丢给播放器用，也可以考虑备份一下，存到网盘或者移动硬盘，
  以后需要的时候就可以方便获取，而不需要重新下载，毕竟 Lucida 说不定也会挂。

  下载的内容先花点时间听一听，验证一下是否存在损坏，
  不用急着一下子下载很多，一次性下载十几张专辑，有的专辑可能很久都不会听。
  不如慢慢地去收集那些真的很喜欢的专辑，那些愿意一听再听的专辑。

  下载的专辑里是没有歌词的，除了在网上搜索歌词，你也可以考虑在博客里写写专辑分享，
  分享自己听歌的感受，将歌词记录在其中，什么时候想看歌词就可以翻出来看。

  最后，力所能及的前提下，也不要一直白嫖，你可以：
  - [[https://lucida.to/donate][捐赠]] 支持 Lucida、宣传 Lucida
  - 在 [[https://bandcamp.com/][bandcamp]] 上购买数字音乐，或者购买 CD、黑胶等支持你喜欢的音乐人
  - 去听喜欢的音乐人的 live，顺便买点喜欢的周边
  - 分享你喜欢的音乐人、专辑

  找电影看，翻了翻待看列表，看到「春天情书」，最近也正好是春天，就选择了这部电影。

  除了男主的网络昵称是「春天（ハル）」，其他和春天似乎都没啥关系。

  影片讲述了两个人在一个电影 [[https://zh.wikipedia.org/wiki/BBS][BBS (Bulletin Board System, 電子佈告欄系統)]] 中认识，
  然后一直通过电子邮件交流，电影一方面展示了两个人的生活，一方面则展示着两个人的通讯。
  两个人在生活中多少都有一些悲伤和失意，但在网络世界中，
  通过电子邮件相互倾诉，找到了一些喘息的空间。

  电子邮件相比即时通讯是有些「慢」的，但正因为这一点「慢」，让人可以有空间、时间去斟酌内容，
  而不像即时通讯一般，想到什么就直接发送。

  影片的节奏是缓慢的，缓缓地叙述着两个人的生活，在网络上相互分享着生活的点滴，
  开心的、难过的、真实的、带着谎言的……

  早期网络上，个人信息很少，交流时不知道对方是谁，
  对方的性别、年龄、样貌…都是通过对话去猜测、认识和想象，往往对对方都会带有一些美好的想象吧。

  后来两人相约见面一次，竟然是一个在新干线上，一个在新干线下，相互挥手帕和录像，憧憬、兴奋、
  想见面却又害怕靠近，之后反反复复地翻看录像，珍惜地收藏着。

  里面网友见面会相互确定一个物件，例如报纸、软盘，也很有趣，但也会很担心自己拿出了信物，
  对方看到自己后不想相认吧。

  概括来说，这是一个早期网络恋爱故事，豆瓣有个热评也很精准「那些 豆邮(1) 的日子。」

  推荐一看。（＾ー＾）

- [[https://store.steampowered.com/app/2379780/Balatro/?l=schinese][Balatro]]

  Balatro，又称小丑牌，前阵子看到打折就买来玩了玩，很上头。

  Balatro 是一个 [[https://zh.wikipedia.org/wiki/%E8%82%89%E9%B8%BD%E6%B8%B8%E6%88%8F][Roguelike]] 游戏，随机生成关卡、小丑牌、卡牌，
  每个关卡会有一个目标分数和限制条件，需要找到一个套路可以尽可能得到高分，达到目标分数。
  爽点就是找到了一个套路后，看卡牌分数不断叠加，比较有成就感吧。

  类似的还有 [[https://store.steampowered.com/app/1404850/_/?l=schinese][幸运房东]] 、[[https://store.steampowered.com/app/3784030/_/?l=schinese][浣熊推币机]]、[[https://store.steampowered.com/app/998740/_Ring_of_Pain/?l=schinese][苦痛之环]] 、[[https://store.steampowered.com/app/2868840/Slay_the_Spire_2/][杀戮尖塔]]……

  这类游戏前期可能比较困难，因为很多道具没有解锁，没法形成套路，
  多玩几局解锁足够道具后，一旦形成套路就会很爽。
  但道具和套路就那些，久了之后也会有些枯燥。

  分享一些我通过过的种子，不过它们的潜力不太行，无限模式下撑不了几关。

  + =V5QX5M2K= 用少量 A 大杀四方
  + =PKULZU82= 人头、单张、塔罗牌、牌型
  + =TJ8FY9PX= 倍率流
  + =346FD34W= 人头牌刷钱流，钱用来产生点数和倍率
  + =YNI14NL4= Q 倍率
  + =NMCNQAVK= 黑桃倍率
  + =9AKPE96H= 红桃倍率流，需要用使用红桃、黑桃牌组，但是当红桃无效的时候就惨了
  + =ZPJ17UVD= 同花流
  + =NL58Z2SV= 对子、倍率流

  所有小丑牌里，我最喜欢的是「流浪者」，钱少于等于 4 块的时候，每次出牌都会生成塔罗牌，很爽。
